# test: regenerate with database timeouts that start after acquire

Local record. The complete design, decisions and risks are in the primary
record, Stumble/wpgx `docs/changelogs/2026-11-20-db-timeout-after-acquire.md`;
the generator change is in Stumble/sqlc
`docs/changelogs/2026-11-20-db-timeout-after-acquire.md`.

## 1. Background and Current State

- Stumble/sqlc's `wicked` CI job regenerates this repository at a pinned commit,
  requires no diff in `pkg/repos`, and runs `go test -race ./pkg/usecases`.
- The committed code was generated by the previous sqlc (`context.WithTimeout`
  at the top of every method) and depends on wpgx v0.3.1 (go 1.22).
- Two runtime contracts encode the old timeout scope:
  `TestWickedDatabaseTimeout` asserts that the context passed to `WQuery`
  carries the 250ms deadline, and `TestWickedCacheTimeout` asserts that the
  Redis `GET` runs under it.

## 2. Problem Model and End-to-End Behavior

- B1 — `pkg/repos` is regenerated by the new sqlc: methods pass their timeout to
  `wpgx.WithDBTimeout`.
- B2 — Runtime contracts follow the approved semantics: a statement blocked in
  the database fails with `wpgx.ErrDBTimeout` after its timeout; waiting for
  the pool's only connection longer than the timeout does not fail the query;
  an unresponsive Redis fails a cached read after the Redis client's
  `ReadTimeout` (not the 250ms query timeout, and well before the caller's
  deadline) and never falls through to the database. This needs dcache v0.3.0+
  without Redis single flight, so the module moves from dcache v0.1.3 (Redis
  single flight always on, go-redis v8) to v0.4.0 (go-redis v9), the version
  every Alva service runs.
- B3 — The module requires the wpgx release with `WithDBTimeout`; go 1.26 and
  the matching CI Go/lint versions follow from wpgx.
- Non-goals: dependency changes beyond wpgx and the dcache/go-redis move B2
  needs; other behavior.

## 3. Research, Findings, and Architecture Decision

See the primary record. Local decisions: rewrite the two contracts instead of
deleting them, so the CI job keeps proving the timeout boundary end to end;
adapt the test-suite constructor to wpgx's current signature (the database name
comes from the config).

## 4. Implementation Design

- `pkg/repos/**`: regenerated, not hand-edited.
- `pkg/usecases/wicked_contract_test.go`: replace the two timeout contracts and
  add the pool-wait contract.
- `pkg/usecases/usecase_test.go`: new `NewWPgxTestSuiteFromConfig` signature.
- `go.mod`/`go.sum`: dcache v0.1.3 → v0.4.0 with go-redis v8 → v9 (imports in
  `internal/testenv` and tests); wpgx bump (pseudo-version of the wpgx branch
  until the release is tagged).
- `.github/workflows/go.yml`: Go from `go.mod` and a golangci-lint version that
  supports it.

## 7. Outcome and Evidence

- Result: `pkg/repos` regenerated by the new sqlc (byte-identical on
  regeneration); contracts `TestWickedDatabaseTimeout`,
  `TestWickedTimeoutExcludesPoolWait` and `TestWickedCacheTimeout` prove the
  database bound, the excluded pool wait, and the Redis-client bound with the
  caller's exact deadline handed to Redis. dcache v0.1.3 → v0.4.0 and
  go-redis v8 → v9 (R1-06); wpgx pinned to
  `v0.5.2-0.20261120053742-4b29cac2136d` (go 1.26.0); CI takes Go from go.mod
  and lints with golangci-lint v2.14.0.
- Verification on 89b3fbc (`GOWORK=off GOMAXPROCS=2`): `go build ./...`,
  `go vet ./...`, `make sqlc sqlc-verify SQLC=<new sqlc>` and
  `git diff --exit-code -- pkg/repos`, `make test`, and
  `go test -race -count=1 -p 1 -timeout 10m ./pkg/usecases` pass;
  golangci-lint v2.14.0: 0 issues. Mutation checks: a 250ms deadline on the
  cache call, and dropping the caller's deadline, each fail
  `TestWickedCacheTimeout`.
